Safety

How Corresync protects your accounts

One local process, the session owner, holds access to your providers and keeps each account separate. Agents get tools, not credentials. The CLI and MCP run the same checks, and neither can send arbitrary provider requests.

Read the rules Get started

Rules

What Corresync enforces

Corresync enforces these in its own code. They don’t rely on the AI client or on MCP annotations.

01

Where credentials are kept

The configuration file has no field for passwords, browser cookies, OAuth grants, or credential-helper output. Browser sign-in happens in a window you can see, and grants are stored in the OS keyring.

02

Each write goes to one account

Each account has its own sessions, profiles, credentials, sync cursors, caches, previews, queues, and audit records. No write goes to several accounts at once.

03

Important changes need a review

For sends, destructive changes, adding or removing accounts, and calendar invitations, the approval only covers the exact caller, account, target, and content you reviewed.

04

Unclear results are not retried

If a provider may have made a change but didn’t confirm it, Corresync asks you to check rather than retrying and risking a duplicate.

05

Monitoring is off by default

Collecting, local notifications, queueing, running a program, releasing content, and sending data off the machine are each turned on separately.

06

Missing features are reported

Results say what the provider supports and what didn’t work. If a requirement is missing, the operation fails rather than being emulated unsafely or sent to another provider.

MCP uses stdio. The session owner does not listen on TCP. The identity of the Unix socket or Windows named pipe is verified before the local bearer token is sent. Shells and desktop apps reach the same session owner even when their environments differ.

How sending works

First a preview, then an approval that must match it

Any change to a recipient, the body, an attachment, an event field, the item version, the account, or the caller cancels the approval.

Short-lived

The approval expires and is held only by the local daemon that issued it.

Works once

A commit that succeeds or fails for good uses up the approval. It can’t be reused for a later action.

Tied to the target

The account, provider, folder or calendar, version, recipients, content, and effect must be exactly what you reviewed.

Same in the CLI and MCP

In MCP, preview and commit are separate tools. Tool annotations never replace Corresync’s own checks.

Sign-in

You choose a route, then sign in when you decide to

The lookup uses no credentials and reports what it found and what sign-in each route needs. It never opens a browser, asks for administrator consent, or adds an account.

Visible browser

Outlook Web

SSO, MFA, Conditional Access, account selection, and provider notices all happen in a separate browser profile.

Public-client OAuth

Google and Graph

Used only when you select it. PKCE, a registered loopback redirect, minimal scopes per service, and grants stored in the OS keyring. A Google Desktop client credential is imported into its own OS keyring entry and never appears in the configuration. Graph needs no client secret.

Local credential reference

JMAP, IMAP/SMTP, and CalDAV

An OS keyring entry or an approved helper (by absolute path) is read only for the selected account and its encrypted endpoint.

Mail content

Nothing in an email can give it permissions

Messages, attachments, calendar fields, imports, links, and monitor queue values are private data an attacker may control. They are never treated as instructions to an agent or as permission to run anything.

Metadata before content

Lists leave out bodies and file contents. Reading sensitive content is a separate, size-limited request, and you can require a preview for it.

Read-only import

One local path you approved can be scanned into a staging area for one account. The import can’t upload, sign in, or change the source.

Opt-in monitoring

Step by step: off, notifications, a queue, then one approved runner started without a shell. Sending data off the machine is a separate choice.

Feedback reports

corr feedback builds a report from allowlisted fields locally and shows it before anything is copied, saved, or opened in a browser. You can also opt in to filing public issues through your signed-in GitHub CLI. That smaller automatic format can’t hold raw errors, values, paths, accounts, credentials, mail, or calendar data, and never runs during MCP work.

Verified updates

Before replacing the binary, a standalone update checks the release identity, checksum, version, and platform. Automatic installation is a separate opt-in and never runs during MCP work. Stable and preview releases are verified the same way. Homebrew, Scoop, and WinGet installs are updated by their package manager and get stable releases only.

Not included

Corresync can’t do more than your account already allows

  • No hosted relay, remote MCP gateway, or telemetry pipeline
  • No password prompt, unattended login, token field, or TLS interception
  • No tenant-wide access, administrator capability probe, or automatic Graph authorization
  • No generic provider property access or arbitrary provider actions
  • No Teams messaging in this release. Calls, recordings, presence, and meeting lifecycle management are out of scope
  • No automatic retry after an ambiguous write

Evidence

Synthetic tests don’t prove a real provider works

v0.8 routes are built and tested against synthetic provider contracts. Google authorization and bounded reads also have one live observation, on macOS arm64 at a specific commit. Other providers and all writes are live-unobserved until an authorized, content-free observation names the exact Corresync commit, provider route, platform, and outcome.

A missing observation is never counted as a pass. The default tests and CI never touch a real mailbox or calendar.
